# Artifact Contracts
<!-- prework:spec-artifact-catalog -->

**One file per artifact. One source of truth per artifact.**

A contract answers four questions: what is this artifact *for*, who *produces* it, who *consumes* it, and what must be *in* it before it counts as done. Each contract ends with the skeleton to copy.

Steps never restate this. A step says "writes `03-agreement.spec.md` per its contract" — that is all. If an artifact's structure changes, it changes here, once.

Artifact prefixes always match the producing step. Human companions are generated projections, never another source of truth: `02-questions.view.html` (step 02, regenerated by step 03), the complete `03-target-solution.view.html`, `03-human-decision-gate.view.md` / `.view.html` (step 03, gate 04), and `08-human-review-gate.view.md` / `.view.html` (step 08). Markdown is the portable fallback and HTML is the preferred primary page; both come from canonical sources. The rule behind them: **every human decision point gets one short reading route, while full design and every acceptance criterion remain visible**.

### Workspace location and paths

All delivery artifacts live in one feature folder. Resolve its location once at kickoff;
the number of component repositories does not decide where artifacts belong.

- **A selected ticket folder:** use `<ticket-root>/delivery/`, with independent code clones
  under `<ticket-root>/repositories/<repo>/`. This is the default when the user starts from
  a ticket folder, including a single-repository delivery. A parent notes repository or a
  host-created checkout of it is not automatically the target code repository.
- **Starting in the target code repository without a ticket folder:** keep the supported
  in-repo layout `docs/sdlc/features/<YYYY-MM>/<story-slug>/`. For a new delivery involving
  other repositories, settle an external ticket root before setup.
- **An existing delivery:** retain its recorded layout, including legacy sibling
  `<story-slug>_workspace/` folders. Never move artifacts or recreate checkouts on resume.

The story slug is the lowercased ticket ID, plus a qualifier only when one ticket has
several deliveries. Without a ticket, derive it from the first meaningful title line:
lowercase, transliterate umlauts, replace non-alphanumerics with hyphens, trim hyphens,
and limit it to 50 characters. Branch names follow repository rules separately.

For new manifests, `workspace_root` is a relative path from the manifest's directory to
the selected ticket root or code-repository root. `folder` is relative to that root.
Resolving both must lead back to the manifest's actual directory. Component locations
are relative to the manifest's directory, independent of placement. For example:

| Placement | `workspace_root` | `folder` | Component location |
|---|---|---|---|
| Ticket folder | `..` | `delivery` | `../repositories/service` |
| In-repo | `../../../../..` | `docs/sdlc/features/2026-10/ticket-123` | `../../../../..` |

Legacy manifests without `workspace_root` keep their existing path meanings: in-repo
`folder` and component `.` are repository-relative; sibling component paths are
manifest-relative. Confirm that the recorded folder resolves to the discovered manifest.
If the root cannot be established uniquely, stop for the missing location instead of
rewriting paths. Use the discovered manifest directory for all artifact reads and writes,
and each declared component directory for Git, builds and code changes. Absolute paths
may be passed to tools and delegates, but are not stored in artifacts.

### Finding an existing delivery

1. Honor an explicitly selected manifest or delivery directory first. A selected ticket
   root is searched for `delivery/00-manifest.state.md` before treating it as a new run.
   A path to input material selects input only; never assume its containing directory is
   the delivery location.
2. From the current directory, inspect ancestors for a manifest directly in the directory
   or under `delivery/`. This also finds the ticket root from inside `repositories/<repo>`.
   Search the target code repository's `docs/sdlc/features/*/*/00-manifest.state.md` for
   legacy in-repo deliveries. Do not recursively search unrelated ticket folders.
3. Match the requested ticket or the package branch when needed. An explicitly selected
   delivery is not rejected because the current shell belongs to a different repository.
   Multiple matches, conflicting ticket identity, or an invalid explicit manifest mean
   stop and name the candidates; never guess or scaffold a second delivery.
4. Read its status and ledgers and keep its paths. A missing field or partial setup in an
   existing delivery is reported for repair, not treated as permission to start again.

### Ticket-root setup

Step 00 owns checkout preparation. For a missing component, clone its verified remote
into `repositories/<repo>`; do not create a worktree backed by another ticket's checkout.
Record the selected base ref and resolved commit. A new clone defaults to the remote's
default branch after fetching; an explicitly requested ref takes precedence. Reusing a
checkout requires checking its remote, root, branch and local changes first. Preserve
explicitly selected existing worktrees; a `.git` file alone is not an error. Later trial
worktrees for ticket deliveries belong under this same ticket root and use its clone.

The ticket root carries an entry file pointing to `delivery/00-manifest.state.md` and its
`## Context Registries` declaration. Use the context plugin's `connect` contract, with the
root and entry-file choice already settled at kickoff. Declared URL registries are kept
under that root's `.sdlc/context/`; component repositories retain their own declarations.
Read applicable declarations and surface conflicts rather than giving one root priority.

Create `delivery/` and its three phase directories up front. Do not create placeholder
artifacts or `.gitkeep` files, and never use an empty directory as evidence of step
completion. Keep supplied `context/`, `FeatureSeed/`, screenshots and seed files unchanged.
Delivery artifacts may be siblings of input folders, but never go inside those folders.
External delivery artifacts are not staged into component repositories or their PRs.

Inside the workspace, three numbered folders group the artifacts by phase; the manifest stays at the root. The rule in one sentence: **the folder digit sorts the phases, the file prefix names the step that produced the file.** A research note spawned during implementation is `1-research/06-<topic>.research.md`: it sorts with the facts, and its prefix says where it came from.

```text
<workspace>/
├── 00-manifest.state.md
├── 1-research/
│   ├── 01-current-solution.research.md
│   └── 06-<topic>.research.md            (example: spawned during step 06)
├── 2-specification/
│   ├── 02-questions.inventory.md
│   ├── 02-questions.view.html
│   ├── 02-work-breakdown.md
│   ├── 03-agreement.spec.md
│   ├── 03-target-solution.spec.md
│   ├── 03-target-solution.view.html
│   ├── 03-test-scenarios.spec.md
│   ├── 03-decision-manifest.state.json
│   ├── 03-human-decision-gate.view.md
│   └── 03-human-decision-gate.view.html
└── 3-planning/
```

## File types

The suffix tells a session how to treat a file before reading a word of it:

| Suffix | Means | Handling rule |
|---|---|---|
| `.spec.md` | what shall be true | frozen once approved at a gate; changed afterwards only through a dated correction or amendment entry (rule 8) |
| `.plan.md` | what shall be done | executed and checked off |
| `.research.md` | what is true today | findings, never decisions — do not treat as intent |
| `.inventory.md` | tracked list with a fill-in lifecycle | items are appended and their answers or statuses filled in; existing item text is never rewritten |
| `.log.md` | append-only record | appended, never rewritten |
| `.state.md` | machine-readable run state | steps mutate it; humans rarely read it |
| `.state.json` | schema-backed machine state | generated and validated fail-closed; humans use its generated views |
| `.view.html` | generated presentation of a sibling artifact | regenerated from its source, never hand-edited; carries no truth of its own |

### Human and machine files have different jobs

JSON state files are the pipeline's small database. They provide fixed IDs, allowed states, links
between records, exact counts, commit and test evidence, approval hashes, deterministic view input,
and fail-closed resume behavior. Markdown remains the source for human reasoning and the full design;
HTML is the primary human reading surface. Humans are never required to inspect raw JSON. JSON should
store state, identity, provenance, evidence and hashes—not long explanations that belong in Markdown.
The decision state also owns the approved work-package-to-acceptance-criterion map. Review can stay
blind to the implementation plan while its validator still proves that the selected package assessed
every required criterion with the exact approved wording.
The validators regenerate human views in memory and compare them byte-for-byte before a gate. Approval
also hashes the complete target-solution HTML. A stale or hand-edited page therefore cannot be approved
while the canonical source says something else.

### Resuming a 0.7.0 workspace

Version 0.7.1 includes an explicit, backup-first state migration:

```bash
python3 <plugin>/scripts/migrate_state_070_to_071.py \
  2-specification/03-decision-manifest.state.json \
  3-planning/07-review-<package-id>.state.json
```

Each original is preserved beside the migrated file with `.v0.7.0.json`. Decision approval reopens so
the human can check the newly added short meanings, reading priorities, and conservative `ALL`
package-to-criterion mapping. When both files are migrated together, review wording and coverage are
reconciled to that canonical map; a previously omitted criterion is added as `NOT_VERIFIABLE` and
therefore cannot produce a Ready verdict. A legacy completed review
resumes after evidence checking with one unbuilt combined trial fix; old candidate results remain in
the backup and are not silently promoted to proof under the new rules. Refine migrated summaries and
priorities before reapproval—the safe defaults preserve exact criterion text and mark it Important.

Definition and instance share the same name: a feature folder's `03-target-solution.spec.md` is valid iff it satisfies the contract file of the same name here.

## Evidence and source maps

Any artifact that states facts may use the evidence system the current-state research defines; the question inventory must. The mechanism, defined in full in [`01-current-solution.research.md`](01-current-solution.research.md):

1. Facts in the body cite short evidence IDs such as `[F2]`; the exact locations live in one `## Source map` at the end, under prefixes declared in `## Source roots`. Every ID resolves exactly once; every map row is cited at least once.
2. Valid sources are code, other artifacts of the same feature, and context-registry articles, each under its own root. Absolute paths are prohibited everywhere.
3. A source-map location may additionally be written as a relative markdown link with line anchors (`path/to/File.java#L42-L60`), so evidence opens directly where the host renders links. The visible text keeps the exact `path:line`, so nothing is lost where links do not resolve.

## Cross-cutting rules

These hold for every artifact and are not repeated in the individual contracts.

1. **The feature folder is the state.** No separate status file. Where a feature stands is visible from which artifacts exist. This is what makes the pipeline resumable and handover-capable.
2. **Acceptance criteria travel verbatim.** From `03-agreement.spec.md` into `05-implementation.plan.md`, into the PR body, into the review checklist. Never rephrased, reordered, or trimmed — otherwise they drift and nobody can verify the feature at the end. The generated human approval pack may sort them by reading priority, but it preserves every original criterion and does not change the canonical order or authority.
3. **Approval lives in the artifact.** Not only in the ticket system. The gate writes status, who, and when into the artifact it approves.
4. **Verify facts against the code, never against older documents.** A stale migration number, endpoint, or field name copied forward from a document is a recurring, expensive failure.
5. **Unfinished is marked unfinished.** `TODO:` and "unresolved" sections are valid content. Plausible-sounding filler is not — it destroys trust in the whole chain.
6. **One step edits only what it owns.** Updating someone else's ledger row or rewriting an upstream artifact breaks the audit trail.
7. **Registry context is consulted and logged.** Every step reads the selected workspace root's and relevant components' entry files explicitly, follows their `## Context Registries` procedures, and records the articles it consulted in a `Context loaded:` line (step 00 in new manifests, step 06 in the plan's progress log, step 07 in its review state). Resolve registry paths from the entry file that declares them. An explicit `- none` or no relevant articles is stated; a missing declaration is not silently treated as none. Keep each step's reading focused on its task.
8. **Approved artifacts change by the amendment protocol, never by rewrite.** A post-approval change is recorded as a dated `Correction:` or `Amendment:` line in the artifact's header, naming what it supersedes, who approved it, and when; the superseded text stays in place, and an affected inventory answer gets a correction sub-entry under the original, never a rewrite. A **correction** changes how an agreed decision is realized; the human approves it in the moment, typically during a review. An **amendment** changes the agreement itself and reopens gate 04 for the delta.
9. **Reviewer findings are not commands.** Step 07 records evidence and source authority before any correction. An independent evidence checker marks each finding valid, wrong, partly right, or human-owned. Compatible valid findings share one trial fix; the original changes only after an independent final checker proves that trial a safe improvement.
10. **Source authority and applicability are explicit.** Ticket text, acceptance criteria, registry rules, reference implementations, approved design, runtime evidence, user decisions, and agent inferences are typed in the decision manifest. No source wins mechanically: conflicts record both claims and consequences, then resolve at the smallest appropriate decision gate. An `_todo_` registry article is missing context, never policy.

## Starting a feature

```bash
mkdir -p docs/sdlc/features/<YYYY-MM>/<story-slug>
# copy the skeleton section out of each contract you need
```

Step 00 scaffolds exactly two files: the manifest and `AGENTS.md`. The numbered folders appear when the first artifact is written into them, and placeholder companions are never created — a workspace shows what has actually happened, not what might.

Optional artifacts (`05-technical-analysis.research.md`, `05-technical-questions.inventory.md`) are only created when the change has real technical depth. A feature has the artifacts it has reached — not all of them, always.
